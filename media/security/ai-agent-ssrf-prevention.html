AIエージェントのURL取得ツールは、SSRFからどう守りますか？

取得ツール側で、URLの正規化、IP検査、redirect制御を強制します。注意書きでは防げません。

Web調査や資料取得を行うAIエージェントには、URLを受け取り、サーバー側からアクセスするツールがよく組み込まれます。ここでモデルが生成したURLや利用者の入力を、そのままfetchする場合を考えます。

SSRF（サーバーに内部向けの通信をさせる攻撃）によって、次の先へ到達される可能性があります。

  • 内部管理画面
  • cloud metadata
  • localhost
  • 非公開API

プロンプトに「内部URLへアクセスしない」と書くだけでは防げません。モデルの判断とネットワーク境界を分離し、取得ツール側で強制する必要があります。

外部ページは信頼できない入力です。ページ内の「この指示を実行せよ」を、エージェントの命令として扱いません。取得内容はデータとして隔離します。SSRF対策とprompt injection対策は、別の防御層です。

取得ツールの安全は、どんな手順で作りますか？

取得対象の分類、URL正規化、IP検査、redirect再検査、資源制限とログの5つです。

  1. 取得対象を2つに分けます。既知の取引先APIや自社ドメインだけを取得するのか、任意の公開Webへアクセスするのかを先に決めます。既知の対象だけなら、scheme、hostname、port、pathをallowlistへ固定します。任意の公開Webが必要な場合は、domain allowlistだけでは足りません。DNS解決後のIP、redirect先、プロトコル、応答サイズ、Content-Typeまで検査します。OWASPも、SSRF対策を2つの場合に分けて示しています。既知の信頼先へだけ送る場合と、任意の外部先へ送る場合です。
  2. URLを標準parserで正規化します。許可schemeは、httpsなど必要最小限に限ります。file:、gopher:、data:、ftp:など、不要なschemeは拒否します。portも80/443など必要なものだけにします。URLに埋め込まれたcredentialは受け付けません。
  3. DNS解決後のIPを検査します。接続直前に解決した全IPを検査します。loopback、link-local、private、multicast、予約済み範囲は拒否します。IPv4だけでなくIPv6も対象です。DNS rebinding（検査時と接続時で解決結果が変わる手口）を考えると、検査時と接続時に別の解決結果を使わない構成が必要です。可能なら、専用のegress proxyで解決と接続を一体化します。アプリ本体から内部ネットワークへ直接到達できないようにします。
  4. redirectごとに再検査します。最初のURLが安全でも、302などで内部URLへ転送されることがあります。不要ならredirectを無効化します。必要な場合は自動追従せず、一段ごとにscheme、host、port、解決IPを再検査し、回数を制限します。取得対象は主responseだけに絞ります。HTML内の画像や埋め込みは、ブラウザのように自動取得しません。
  5. 資源制限を入れ、ログとテストで確かめます。timeout、最大redirect、最大response bytes、許可Content-Typeを設定します。ログには、request ID、呼び出したtool、入力host、解決先の分類を残します。判定、response size、redirect回数、error classも残します。テストには、localhost、private IPv4、IPv6 loopbackを含めます。link-local、数値IPも含めます。redirect、DNS rebinding相当、巨大response、遅いresponseも含めます。

うまくいかない例には、どんなものがありますか？

文字列の前方一致、domainだけの許可、redirectの自動追従、特定クラウドの設定への依存が典型です。

  • 前方一致で済ませます。見た目と実際の接続先が異なる入力があります。例は、https://example.com.evil.invalid、userinfoを含むURLです。Unicodeや末尾ドット、IPv6表記もあります。
  • domainのallowlistだけで済ませます。hostnameが公開名でも、DNSがloopbackやprivate addressを返す場合があります。
  • redirectを自動で追います。最初のURLの検査だけでは、転送先の内部URLを防げません。
  • 巨大なファイルや終わらないstreamを許します。公開URLでも、可用性を損ないます。PDFや画像が必要なら、別経路でsandbox処理します。取得プロセスへ、秘密情報や広い権限を渡しません。
  • 特定クラウドの設定だけに頼ります。AWSはメタデータサービスへの防御としてIMDSv2を提供します。ただし、特定クラウドの設定だけでは、次を防げません。localhost、IPv6、redirect後の再解決、社内APIへの到達です。入力検査とegress制御の片方だけに依存しません。
  • URL全体をそのままログに残します。URLにtokenや個人情報が含まれる場合があります。query stringは、既定で保存しません。
  • 正常系だけを試験します。拒否がfail-closeで働くことを、確認します。

検査の層ごとに、何を見て何を防ぎますか？

URL解析、解決後のIP、redirect、資源制限の4層で、見る対象と防ぐ入力が違います。

層見るもの防ぐ入力の例
URL解析scheme、hostname、port、userinfo。標準parserで正規化するhttps://example.com.evil.invalid、file:、gopher:、埋め込みcredential
解決後のIP接続直前に解決した全IP（IPv4とIPv6）公開名がloopbackやprivate addressへ解決される場合、DNS rebinding
redirect一段ごとのscheme、host、port、解決IPと回数302などによる内部URLへの転送
資源制限timeout、最大response bytes、許可Content-Type巨大ファイル、終了しないstream

よくある質問

「内部URLへアクセスしない」とプロンプトに書けば、SSRFを防げますか？

防げません。モデルの判断とネットワーク境界を分離し、取得ツール側で強制する必要があります。URLの正規化、解決後のIP検査、redirectの再検査を行います。専用egress proxyなどで、アプリ本体から内部ネットワークへ直接到達できないようにします。

ドメインのallowlistだけでは、なぜ足りないのですか？

任意の公開Webを取得する場合は、足りません。hostnameが公開名でも、DNSがloopbackやprivate addressを返す場合があります。redirectで内部URLへ転送されることもあります。DNS解決後のIP、redirect先、プロトコル、応答サイズ、Content-Typeまで検査します。

redirectはどう扱えばよいですか？

不要なら無効化します。必要な場合は自動追従せず、一段ごとにscheme、host、port、解決IPを再検査し、回数を制限します。HTML内の画像や埋め込みをブラウザのように自動取得せず、取得対象は主responseだけに絞ります。

次の一歩は何から始めればよいですか？

取得対象を2つに分け、実際に到達できるネットワークとデータの境界を棚卸しするところからです。
