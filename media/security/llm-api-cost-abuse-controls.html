LLM APIの高額請求は、何を分けて制御すれば防げますか？

request数、実費、tool実行の3つを別の予算にして重ねます。rate limitだけでは防げません。

生成AIの利用制御を「一分に何回まで」にしても、高額請求や可用性低下は十分に防げません。短い要求を大量に送る濫用と、長い入力や高価なモデルを使う処理は、同じ回数でも消費する資源が大きく異なるためです。何段ものtool（エージェントが呼び出す検索や送信などの機能）を動かす処理も同じです。

OWASPは、過剰で制御されない推論を「Unbounded Consumption」として整理しています。DoS（サービスを止める攻撃）、経済的損失、model theft、サービス低下につながる脅威です。大きなcontext、長い出力、複数回のretry、agent loopは、少ない操作でも高い消費になり得ます。

結論として、制御対象は次の3つの予算に分けます。

  1. request予算は、短時間に入口へ届く回数です。botや偶発的な再送から可用性を守ります。
  2. spend予算は、model・provider・token使用量から推定される金額です。token（AIが読み書きする文字量の単位）の多い処理による請求を抑えます。
  3. action予算は、1回のエージェント実行で許す検索、取得、書込み、外部送信、後続jobの回数です。model呼出し後の暴走を抑えます。

反対に、同じ利用者が短い問い合わせを数回行うことまで一律に止めると、正当な業務を妨げます。

自社ではAI利用料の見張りをどうしていますか？

代表の古野がClaude Codeの利用額を、応答ごとの表示と毎朝のSlack通知で見ています。

ここでの例は、TechWorker代表の古野が毎日使っているClaude Codeの利用料の見張り方です。APIゲートウェイの設定例ではありません。

古野の端末の利用記録を、集計ツール（ccusage）でAPI料金に換算しました。2026年9月14日から30日の17日間で、約3,000ドル分です。1日平均は約180ドル分です。

日によって差は大きく、少ない日は約4ドル分、多い日は約850ドル分でした。200倍以上の開きがあります。1日の回数や平均だけを見ても、この偏りは読み取れません。

そのため、次の2つで支出を見えるようにしています。

  • 1回の応答ごとに、その回と累計の推定額を画面の下に表示します。
  • 前日の利用額が、毎朝社内のSlackに届きます。

換算額は実際の請求額とは異なります。定額の範囲内の利用には、追加の支払いは発生しません。この見張り方は、次の手順で実費を別の予算として扱う考え方と同じ方向です。

上限は、どんな手順で設計すればよいですか？

入口、実費、tool実行の順に上限を置き、上限のキーと429の扱いまで決めます。

  1. 入口にrate limitを置きます。AI Gatewayのrate limitingは、gatewayへ送れる回数を時間枠で制御します。固定windowとsliding windowを選べます。上限を超えると429 Too Many Requestsを返し、処理しません。急な連打や認証前の濫用に有効です。
  2. 実費にspend limitを置きます。spend limitは、token使用量とmodel pricingから累積コストを追います。上限に達すると429でブロックします。model、provider、custom metadataの組み合わせで範囲を分けられます。全社の総額だけでなく、teamやapplication単位の予算も作れます。
  3. 上限のキーを認証済みの情報で作ります。IPアドレスだけで制限すると、企業ネットワークやプロキシ配下の正当な利用者が同じ枠を取り合います。認証済みの利用者、テナント、アプリケーション、model、操作種別を組み合わせます。Cloudflare Accessで保護したcustom domainなら、認証済みのIDが付きます。IDはcf.user_id metadataとして、利用者別のspend limitに使えます。
  4. tool予算と停止条件を別に持たせます。1回のmodel requestを通しても、その応答が10回の検索や外部更新を選べば、後段の負荷は残ります。エージェント実行ごとに、最大tool回数と最大並列数を決めます。最大wall time、最大取得bytes、最大queue投入数も決めます。上限に達したら理由を利用者へ返して止めます。
  5. 429を安全な状態として設計します。画面には「上限に達した」「いつ再試行できるか」「結果が未作成か」を示します。同じ操作IDの二重起動を防ぎます。バックグラウンドjobは、上限に達した理由と再開条件を記録し、無条件のretryを避けます。

うまくいかない例には、どんなものがありますか？

rate limitだけで済ませること、利用者名を画面入力から受けること、黙って安いmodelへ変えることが典型です。

  • rate limitだけを置きます。同じ回数でも消費は同じではありません。spend limitとtool予算を重ねます。
  • user_idを画面入力から受け取ります。Accessを通さない場合はcustom metadataを渡せます。ただし、クライアントが任意のuser_idを名乗れる設計では、予算回避や他者へのなりすましを招きます。識別子は認証済みのserver側の情報から付けます。
  • 上限に達したら黙って安いmodelへ切り替えます。要約や候補生成のように品質条件を決めた処理なら選択肢になります。契約文書、顧客への外部送信、次の操作が変わる分類では、モデル変更が品質と説明責任を変えます。許す操作を業務側と先に合意しておきます。
  • gatewayの表示を会計の正本にします。AI Gatewayはcostをbest-effort estimation（できる範囲での推定）として扱います。正確な請求額は、providerのdashboardで確認するよう明記しています。照合の経路を残します。
  • 429を受けて即時に再試行します。制限そのものを増幅させます。
  • 厳しすぎる上限を全社一律で置きます。月末や障害時の正当な利用まで止まります。利用目的ごとに安全に止められる経路を作り、実測した消費と業務影響から見直します。
  • 予算内なら外部送信してよいと考えます。課金予算は認可の代わりになりません。MCPや外部toolの権限は、OAuth認可の設計で狭めます。外部送信や更新には、AIエージェントの承認ゲート設計も必要です。

上限は消費を制御するだけです。prompt injection、誤った権限、情報漏えい、誤答は防ぎません。「上限を置いたから請求は必ずこの額以下」とは書かないでください。providerの個別契約、割引、税、遅延した利用集計は、spend limitの推定に含まれません。

3つの予算は、それぞれ何を抑えますか？

request予算は入口の回数、spend予算は実費、action予算はtool実行を抑えます。表で整理します。

予算抑えるもの代表的な手段残る限界
request予算短時間の連打、認証前の濫用、偶発的な再送AI Gatewayのrate limiting（固定window・sliding window）。超過時は429同じ回数でもコストは同じではない
spend予算長い入力や高価なmodelによる実費の偏りAI Gatewayのspend limits。model・provider・metadataで範囲を分けるbest-effort estimationで、請求額の正本ではない
action予算1回の実行で起きる検索、取得、書込み、外部送信、後続job最大tool回数、並列数、wall time、取得bytes、queue投入数操作の正当性は別の承認・監査で確認する

よくある質問

rate limitだけで、LLM APIの高額請求を防げますか？

防げません。rate limitは、一定時間のrequest数を抑えます。長い入力や高価なmodelは、同じ回数でも消費が大きく異なります。入口のrate limit、token使用量のspend limit、tool回数のaction予算を重ねて設計します。

利用者別の上限は、何をキーにして設けますか？

IPアドレスだけにせず、認証済みの利用者、テナント、アプリケーション、model、操作種別を組み合わせます。クライアントが任意のuser_idを名乗れる設計は、予算回避やなりすましを招きます。識別子は、認証済みのserver側の情報から設定します。

上限に達したときは、より安いmodelへ自動で切り替えてよいですか？

要約や候補生成のように品質条件を決めた処理に限ります。契約文書、顧客への外部送信、次の操作が変わる分類では、モデル変更が品質と説明責任を変えます。許す操作を業務側と先に合意し、理由を利用者へ返して停止する設計を基本にします。

次の一歩は何から始めればよいですか？

実装前のチェックリストを埋めてから、必要ならセキュリティレビューで設計を確認します。

  • request、spend、tool actionの3つを別の上限として定義したか
  • 利用者、テナント、アプリ、modelのどれで予算を分けるか説明できるか
  • 料金・権限に使う識別子を、認証済みserver側の情報から付けているか
  • 固定windowとsliding windowのどちらが、burst（短時間の集中）を許す業務に合うか決めたか
  • spendの推定値とprovider請求額を照合する担当・周期を決めたか
  • 上限時に429を返し、同じ操作を無条件にretryしないか
  • tool回数、取得bytes、並列数、queue投入数にも停止条件を置いたか
  • fallback modelを許す操作・品質条件・利用者への表示を決めたか

上限やtool権限の設計をご相談の方は、MCP・AIエージェントのセキュリティレビューをご利用ください。
