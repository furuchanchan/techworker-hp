MCPサーバーのOAuth認可は、配布元の確認と何が違いますか？

配布元の確認は導入前の検査で、OAuth認可は実行ごとの制御です。両方が必要です。

MCPサーバーを企業へ導入するとき、Registry上の表示名、配布元、SBOM、署名、固定版を確認することは重要です。ただ、それだけでは実行時の安全性を説明できません。

正規のMCPサーバーでも、広すぎるtokenを受け入れれば、意図しない権限行使につながります。別の接続先向けのtokenを使える場合も同じです。

配布元や署名の確認は、「何を導入するか」の検査です。OAuth認可は、「導入済みのserverに、誰が、どの範囲で、どのtokenを使って要求するか」の制御です。

悪意あるserverは、認可フローが正しくても導入してはいけません。逆に正規のserverでも、全社共有の管理tokenを渡せば、利用者・接続先・操作範囲を限定できません。供給経路と実行権限は、別のチェックリストで扱います。

結論は次のとおりです。

  • どのserver向けのtokenかを、resourceで固定します。
  • 必要最小限のscopeを、段階的に要求します。
  • 盗まれたtokenの再利用を、短命化・sender constraint・失効で抑えます。
  • 人の承認は、この認可境界を通った後の高リスク操作に置きます。

本記事は、9月7日に確認したMCP Authorization specificationが対象です。版は2025-11-25です。ローカルstdio接続には、HTTP/OAuthのdiscoveryをそのまま当てはめられません。transportごとに境界を分けてください。

リモートMCPの認可は、どんな手順で設計しますか？

認可先の発見、resourceの固定、scopeの絞り込み、盗用への備え、service tokenの分離です。

  1. 正しい認可先を発見させます。現行の仕様では、MCP serverがProtected Resource Metadata（RFC 9728）を実装します。clientは、そこから認可serverを発見します。入口は、401応答のWWW-Authenticate headerか、well-known URIです。401応答は、MCP endpointが返します。clientが偽のmetadataへ誘導されないよう、endpointと認可serverの対応を仕様に沿って検証します。metadataは、認可境界の一部として扱います。
  2. resourceでtokenの宛先を固定します。MCP clientは、2種類のrequestの両方で、対象serverのURIをresourceとして送ります。2種類とは、authorization requestとtoken requestです。RFC 8707のresource indicatorは、tokenを特定のresourceへ結び付けます。別resourceへの転用を防ぐ仕組みです。接続先ごとにresourceを分け、広いtokenを複数serverへ渡しません。テナントをURIのpathで区別する設計では、audienceがテナント境界まで絞れるかを確認します。pathを増やすだけでは、隔離は成立しません。
  3. scopeを業務上の操作に合わせて小さく定義します。scope名に万能の標準はありません。検索だけなら読取、下書き保存なら保存、のように分けます。外部送信・支払い・削除は、別scopeにするか、scopeに加えて人の承認を求めます。最初の接続で将来の権限まで要求せず、追加操作の直前に求めます。利用者への説明と監査がしやすくなります。
  4. tokenの盗用と再利用を前提に備えます。OAuth 2.0 Security Best Current Practice（RFC 9700）は、4つの対策を示しています。redirect URIの完全一致とPKCEです。refresh tokenのrotationとsender-constrained tokenも示しています。PKCEは、認可codeを盗まれても、第三者がtokenへ交換しにくくする仕組みです。code verifierを持たない相手は、交換できません。DPoPは、tokenを特定の鍵へ結び付け、盗んだtokenを別環境で再利用しにくくします。DPoPを使うresource serverは、要求中のproofとtokenに結び付く公開鍵を検証します。
  5. service tokenを無人処理に限ります。Cloudflare Accessのservice tokenは、自動処理を守るcredentialです。ブラウザでログインしない処理が対象です。期限、rotate、renew、disable、revokeを管理できます。定期同期やCIのような、明確な無人処理に向きます。無人処理、利用者委任、高リスク操作を、同じtokenで処理しないことが基本です。

うまくいかない例には、どんなものがありますか？

共有の広いtoken、scopeの出し過ぎや細かし過ぎ、DPoPへの過信、service tokenの流用です。

  • 全社共有の管理tokenを渡します。利用者・接続先・操作範囲を限定できません。
  • scopeを広く要求し続けます。将来必要かもしれない権限まで最初に求めると、説明と監査が難しくなります。
  • scopeを細かくし過ぎます。実装・運用・利用者体験が壊れます。読取、下書き保存、外部作用、管理操作のような少数の境界から始めます。実際の権限昇格を観測して見直します。
  • DPoPをHTTPSの代替と考えます。DPoPはHTTPSの代わりになりません。client本体が侵害され、tokenと鍵の両方を盗まれた場合も解決しません。短い有効期限、refresh tokenのrotation、失効手順、異常利用の検知を組み合わせます。
  • service tokenを人の委任権限として使います。service tokenは、「誰が今回この操作を許可したか」を表しません。利用者ごとの委任や承認履歴が要るMCP toolには、共有の静的credentialを流用しません。
  • 正しい認可を安全の保証と考えます。正しいscopeのtokenでも、prompt injectionで危険な操作が選ばれ得ます。認可は「許可された操作か」を判定する境界です。「今実行してよいか」までは判断しません。外部送信、削除、支払い、顧客データの公開には、人の承認と監査ログが必要です。操作内容を固定した承認と、fail-closeのtimeout設計を置きます。
  • 仕様への対応を確かめません。MCP仕様と各clientの実装対応は更新されます。利用するclient・identity provider・proxyが対応しているかを、導入前の接続テストで確認します。

認可の手段ごとに、何を固定し、何が残りますか？

resource、scope、PKCE、DPoP、service tokenで、固定する対象と残る限界が違います。

手段固定するもの抑える問題残る限界
resource（RFC 8707）tokenの宛先別のresourceへのtoken転用URI設計は既存の認可モデルと合わせて決める
scope許可する操作の範囲広すぎる権限の付与細かくし過ぎると運用が壊れる
PKCE（RFC 7636）認可codeとclientの結び付き認可codeの途中での盗用tokenの盗用そのものは別の対策が要る
DPoP（RFC 9449）tokenと鍵の結び付き盗んだtokenの別環境での再利用HTTPSの代替ではない。tokenと鍵の両方が盗まれると効かない
service token（Cloudflare Access）無人処理のcredentialブラウザ不在の自動処理の保護誰が許可したかを表さない

よくある質問

MCPサーバーの配布元や署名を確認すれば、認可の設計は不要ですか？

不要にはなりません。配布元や署名の確認は、何を導入するかの検査です。OAuth認可は、導入済みのserverに誰がどの範囲でどのtokenを使って要求するかの制御です。正規のserverでも、全社共有の管理tokenを渡せば、利用者や操作範囲を限定できません。

MCPのtokenを、別のserverでも使い回せないようにするには？

clientが、対象MCP serverを表すURIをresourceとして送り、tokenの宛先を固定します。送る先は、authorization requestとtoken requestの両方です。複数のserverへ一つの広いtokenを渡さず、接続先ごとにresourceを分けます。

正しいscopeのtokenを使っていれば、危険な操作は防げますか？

防げません。正しいscopeを持つtokenでも、prompt injectionによって危険な操作が選ばれ得ます。認可は許可された操作かを判定する境界で、今実行してよいかまでは判断しません。外部送信や削除には、操作内容を固定した人の承認と監査ログが必要です。

次の一歩は何から始めればよいですか？

導入前チェックリストで現状を確かめ、必要ならセキュリティレビューで設計を整理します。

  • 対象がremote HTTP MCPか、local stdio MCPかを区別しているか
  • MCP endpointごとにProtected Resource Metadataと認可serverの対応を確認したか
  • clientが2種類のrequestの双方に、正しいresourceを送るか
  • serverが自分向けに発行されたtokenだけを受け入れるか
  • scopeを読取、保存、外部作用、管理操作などの業務境界で分けたか
  • redirect URIの完全一致とPKCEをテストしたか
  • token期限、refresh rotation、revoke時の失効確認を運用手順へ入れたか
  • 401、期限切れ、scope不足、別resource向けtoken、DPoP proof不正を自動テストしたか
  • 外部送信・削除・支払いには、認可とは別に承認ゲートを置いたか

導入前に認可と承認ゲートを整理したい方は、MCP・AIエージェントのセキュリティレビューをご利用ください。
