MCP Appsのセキュリティ設計｜iframe・CSP・postMessage・書込み操作をどう守るか【2026】

MCP Appsの安全は、iframeに頼らず、権限・通信・承認の3つを分けて確認することから始まります。
第三者UIを会話内に表示したいが、書込み操作が心配な、情シスや開発責任者の方の悩みに向けた記事です。

MCP Appsは、iframeで表示すれば安全ですか？

安全とはいえません。iframeは表示を隔離しますが、UIが要求したtool callの実行で副作用は起こります。

MCP Appsは、MCP serverが返す対話UIを表示する仕組みです。hostがsandboxed iframeで表示し、UIとhostの通信はJSON-RPCで扱います[1]。

iframe sandboxは、parent pageのDOMへ直接触れないようにします。cookieやlocal storageも同様です。ただし、UIが要求したtool callをhostが実行できれば、書込みやデータ取得という副作用は起こり得ます。

そのため、次の4点を別々に確認します。表示の隔離、外部通信の制限、messageの送信元検証、tool権限と承認です。

MCP Appsの安全設計は、どんな手順で進めますか？

権限の棚卸し、CSPのallowlist、postMessageの検証、書込みの段階分けの順に進めます。

  1. Appの権限を2つに分けて棚卸しします。「画面に表示する権限」と「外部へ作用する権限」に分けます。MCP Appsのtool UI templateは事前宣言できます。hostは、render前に取得・cache・security reviewできます[2]。tool schemaとは別に、次を整理します。どのtoolがUIを出すか、画面がread-onlyか、保存・送信・削除を要求し得るかです。請求、CRM更新、権限変更、公開、削除は、server側のtool policyで拒否または承認待ちにします。UI上のbutton labelには頼りません。
  2. CSPをApp固有のallowlistとして扱います。CSP（Content Security Policy、読み込みや通信を許す先の宣言）です。MCP AppsのHTMLは、sandboxed iframeで動きます。same-originの通常のweb appとは異なります。network requestを行うAppは、_meta.ui.cspにoriginを宣言します。connectDomainsは、fetch、XHR、WebSocket向けです。resourceDomainsは、script、style、image、font向けです[3]。開発時のlocalhostも含め、実際に必要なoriginだけを明示します。https:のような広い指定や、便宜上のwildcardは避けます。
  3. postMessageを検証します。iframeとhostのpostMessageは、文字列を受け取るだけの実装にしません。MCP AppsのPostMessageTransportは、windowを必須にします。event.sourceを照合するためです。view側はwindow.parentを渡します。host側は、対象iframeのcontentWindowを渡します[5]。hostは、messageのschema、request ID、許可したmethod、対象toolを検証します。想定外のmessageは、fail-closeで拒否します。
  4. 書込み操作を3段階に分けます。read、reversible write（戻せる書込み）、不可逆・高影響の3段階です。readは、必要最小限のscopeで自動実行を検討できます。戻せるwriteは、対象・差分・実行主体をpreviewし、監査可能にします。送信、公開、権限変更、削除、支出は、host側で人の確認を要求します。承認の対象は、tool名だけでなく、arguments、対象record、effectまで固定します。
  5. 対象hostで実測します。MCP Appsは、2026年1月にofficial extensionとして公開されました。ChatGPT、Claude、Goose、Visual Studio Codeのsupportが案内されています[7]。hostごとに、次の点が異なります。supportするcapability、承認UI、CSPのhost-specific originの扱いです。対応clientを推測せず、実測します。試す項目は、read tool、write tool、拒否です。CSP違反、message偽装、network errorも試します。

ChatGPTのdeveloper mode向け公式案内は、書込み系actionの扱いを示しています[6]。contextと影響に応じたconfirmationを求めます。危険操作のblockも示しています。adminによる事前test・vetも示しています。

MCP Appsの設計がうまくいかない例には、どんなものがありますか？

UIの見た目を信用する、CSPを万能と考える、Appの説明で承認する、の3つが典型です。

  • UIの見た目を操作先の証明と考える。UIがきれいに見えても、操作先が正しいとは限りません。
  • CSPを万能と考える。CSPは、prompt injection、XSS、認可不備を解決する代替手段ではありません。W3Cは、CSPをcontent injectionの被害を抑えるdefense-in-depth（多層防御）と位置付けています。入力検証やoutput encodingの代わりではないと明記しています[4]。CSPに通したCDNやAPIが侵害された場合、allowlistだけでは安全性を保証できません。
  • 外部の内容を操作命令として扱う。Appが外部文書、検索結果、MCP tool outputを表示するなら、その内容は非信頼データです。操作命令として扱いません。
  • Appの説明やmodel outputで承認する。Appが「この操作は安全」と説明しても、approval判断を表示文言やmodel outputへ委ねません。
  • CSPとCORSを混同する。CSPは、browserに何を許すかを決めます。CORSは、API serverがどのoriginを受け入れるかを決めます。別の層です。片方だけを通しても、意図した通信になるとは限りません。
  • MCP server自体の信頼を前提にする。MCP server自体が信頼できない場合のリスクも、OpenAIは明示しています[6]。prompt injectionのriskです。

書込み操作は、段階ごとにどう扱いますか？

readは自動実行を検討し、戻せるwriteはpreviewと監査、不可逆・高影響はhost側の人の確認を求めます。

段階例扱い
read情報の取得必要最小限のscopeで自動実行を検討
reversible write下書き保存など戻せる書込み対象・差分・実行主体をpreviewし、監査可能にする
不可逆・高影響送信、公開、権限変更、削除、支出host側で人の確認を要求し、承認対象をarguments・対象record・effectまで固定

よくある質問

MCP Appsは、iframeで表示されるので安全といえますか？

いえません。iframe sandboxは、親ページのDOMやcookieへの直接アクセスを防ぎます。ただし、UIが要求したtool callをhostが実行できれば、書込みやデータ取得という副作用は起こり得ます。表示の隔離、外部通信、message検証、tool権限と承認を別々に確認します。

MCP AppsのCSPは、どう設定しますか？

App固有のallowlistとして扱います。network requestを行うAppは、_meta.ui.cspに、実際に必要なoriginだけを宣言します。https:のような広い指定やwildcardは避けます。CSPはprompt injectionや認可不備の代替になりません。被害を抑える補助層です。

Appからの書込み操作は、どう承認しますか？

read、戻せるwrite、不可逆・高影響の三段階に分けます。戻せるwriteは、対象と差分をpreviewして監査可能にします。送信・公開・権限変更・削除・支出は、host側で人の確認を求めます。承認の対象は、tool名だけでなく引数や対象recordまで固定します。

次の一歩は何から始めればよいですか？

Appが要求し得るtool callを棚卸しし、書込みの段階を決めてから、対象hostで実測します。

  1. AppごとにUIが要求し得るtool callを洗い出します。
  2. CSPのoriginを必要最小限に絞り、書込みを3段階に分けます。
  3. 対象hostで、拒否、CSP違反、message偽装を実測します。
