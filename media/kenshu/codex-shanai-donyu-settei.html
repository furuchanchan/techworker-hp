Codexの社内導入｜管理者が決める設定・サンドボックスと承認・データの扱い

Codexを社内に広げる前に情シスが決めることを、OpenAIの公式文書（2026年11月23日確認）で整理します。6つの管理範囲、requirements.tomlでの承認とサンドボックスの固定、Codex Cloudの接続先、データと監査、自動化の認証、展開の順番まで扱います。

Codexを社内に広げる前に、情シスが決めることは次の3つです。

  • 誰に使わせるか：ワークスペースのシートとロールで決めます。グループごとに機能を分けるカスタムロール（RBAC）は、EnterpriseとEduの機能です。
  • 何を自分で実行させるか：requirements.toml（管理者が配る要件のファイル）で、承認とサンドボックスの選べる値を絞ります。社員はこの要件を上書きできません。
  • データをどう扱うか：BusinessもEnterpriseも、既定では業務データを学習に使いません。保持期間の設定、データの置き場所の指定、監査ログはEnterpriseとEduの機能です。

料金とプランの選び方は、Codexの法人契約と料金にまとめています。この記事では、OpenAIの公式文書（2026年11月23日確認）をもとに、設定と展開の手順を扱います。

原文“By default, the agent runs with network access turned off. Locally, Codex uses an OS-enforced sandbox that limits what it can touch (typically to the current workspace), plus an approval policy that controls when it must stop and ask you before acting.”

日本語訳既定では、エージェントはネットワークにつながない状態で動きます。ローカルでは、OSが強制するサンドボックスが、Codexの触れる範囲を制限します（通常は今の作業フォルダ）。さらに承認の方針が、Codexが作業を止めて利用者に確認する場面を決めます。

出典：OpenAI「Agent approvals & security」（2026年11月23日確認）

管理者の仕事はこの既定の範囲を会社の決まりとして固定し、必要な所だけ広げることです。

許可は6つの管理範囲に分かれる

公式の「ロールとワークスペースの権限」は、許可を6つの管理範囲に分けています。ある範囲で許可しても、ほかの範囲は自動では許可されません。

たとえば、ワークスペースでCodexを使えるようにしても、GitHubのリポジトリを読む権限は付きません。リポジトリの権限はGitHubの側で決まります。ローカルの権限の設定でも、モデルを使う権利は与えられません。

リクエストが通るのは、関係するすべての範囲で許可されているときだけです。設定の担当を、この6つの範囲ごとに決めておくと漏れが減ります。

BusinessとEnterpriseでは、管理できることがどう違いますか？

既定で学習に使わないこと、SAML SSOとMFA、クラウドで管理する設定は両方にあります。RBAC、SCIM、データ保持とデータレジデンシー、監査ログはEnterpriseとEduだけです。

管理・セキュリティの機能BusinessEnterprise・Edu
既定でビジネスデータを学習に使わないありあり
SAML SSO、MFA、ワークスペースのユーザー管理ありあり
requirements.tomlによる設定管理ありあり
クラウドで管理する設定ポリシーありあり
自動化のためのCodexアクセストークンありあり
RBACとカスタムロールなしあり
SCIM、EKM、ドメイン検証なしあり
データ保持とデータレジデンシーの管理なしあり

接続済みのGitHubリポジトリ向けのCodex Securityなしあり

出典：OpenAI「料金」の機能の表、管理・セキュリティ・分析の行（2026年11月23日確認）。公式の日本語版はAIによる翻訳と明記されています。

BusinessはSSOとMFAを使える専用のワークスペースです。ただし、社員の追加と削除をID基盤から自動で同期するSCIMはありません。監査や調査の記録をSIEM（セキュリティのログを集める仕組み）へ送るなら、Enterpriseを選びます。

Businessの料金と、Enterpriseの見積もりの取り方は、Codexの法人契約と料金で扱っています。

誰にCodexを使わせるかは、どこで決めますか？

ワークスペースの管理画面で決めます。シートが使える製品の範囲を決め、組み込みのロールが管理の権限を決めます。

組み込みのロールはオーナー、管理者、メンバー、分析閲覧者です。オーナーはワークスペース全体の設定を管理します。メンバーには管理の権限がありません。

EnterpriseとEduでは、カスタムロールで機能ごとの許可を分けられます。作れるのはオーナーだけで、割り当てる先はグループです。グループは手で作るか、SCIMで同期します。運用では次の2点に気をつけます。

  • ロールの許可は足し算です。割り当てたロールのどれか1つが許可すれば、ほかのロールでオフにしていても使えます。
  • 変更が反映されるまで、最大5分かかります。ロールを変えた直後の確認は、5分ほど待ってからが確実です。

Codex Cloudとモデルの初期設定

Enterpriseのワークスペースでは、Codex Cloudは既定でオフです。クラウドでCodexを使う権限と、共有の環境を作り変える権限は別に付けます。後者のワークスペース環境を管理する権限も、既定でオフです。

使えるモデルも管理者が決めます。EnterpriseとEduでは、GPT-6.2 Astra、GPT-6.2 Sol、GPT-6.1 Solが既定で無効です。管理者がワークスペースのモデル設定で有効にします。Enterpriseの管理者はモデルごとに推論強度と速度の上限も置けます。

チャット向けのモデル設定はCodexのCLIやIDE拡張機能にそのまま適用されるとは限りません。初期設定は、Chat向けと、Work・Codex向けを別々に指定できます。

ローカルのCodexは、どこまで自分で実行できますか？

既定では、書き込めるのは作業中のフォルダの中だけで、ネットワークには出られません。その外へ出る操作の前に、承認を求めます。

仕組みは2つの組み合わせです。サンドボックスは技術的にできることの範囲を決めます。承認の方針はその範囲を超える前に止まって確認する場面を決めます。

サンドボックスのモードできること
read-onlyファイルを読むだけのモードです。編集には承認が要ります。
workspace-write（既定）作業フォルダの中で編集し、日常のコマンドを実行できます。フォルダの外の編集とネットワークは、承認が条件です。
danger-full-accessファイルとネットワークの制限が外れます。

workspace-writeでも、.git、.agents、.codex、.awsの各フォルダは読み取り専用で守られます。承認の方針はon-request（必要なときに確認する）とnever（確認しない）の2つです。以前のuntrustedは廃止され、設定に残っていると起動できない場合があります。

承認を別のエージェントに任せる自動レビュー

approvals_reviewer = "auto_review" にすると、承認の依頼を、人の代わりにレビュー担当のエージェントが審査します。デスクトップアプリでは「代わりに承認（Approve for me）」として選べます。自動レビューが止めるように作られているのは、次の4種類の操作です。

  • 非公開のデータや認証情報を、信頼できない宛先へ送る操作
  • 認証情報、トークン、Cookieを探り出す操作
  • セキュリティを広く、または続けて弱める変更
  • 取り返しのつかない損害を出すおそれが高い、破壊的な操作

同じターン（1回の依頼への応答）で3回続けて拒否されると、Codex CLIはそのターンを止めます。直近50件のレビューで拒否が10回に達した場合も止まります。

公式の説明では、自動レビューは安全を保証する仕組みではありません。判断を誤ることがあり、サンドボックスの設計と監視の代わりにはなりません。レビューのためにモデルを追加で呼ぶので、使用量が増えることもあります。

社員が設定を緩めないようにするには、どうしますか？

requirements.toml（管理者が適用する要件）で、社員が選べる値を絞ります。要件は社員が上書きできません。

要件で絞れるのは、承認の方針、承認のレビュー担当、サンドボックスのモード、権限プロファイル、ウェブ検索、MCPサーバー、プラグインの入手元などです。社員の設定が要件に反すると、Codexは要件に合う値に切り替えて知らせます。

公式の例では次の2行で --ask-for-approval never と、フルアクセス（--yoloを含む）を止めます。

allowed_approval_policies = ["untrusted", "on-request"]
allowed_sandbox_modes = ["read-only", "workspace-write"]

ここで許可リストに入れるuntrustedは、プロジェクトの信頼レベルに基づく厳しい承認を残すための値です。廃止された approval_policy = "untrusted" を使えるようにするものではありません。

Codex 0.138.0以降はsandbox_modeの代わりに権限プロファイルを使うよう推奨されています。管理者向け導入ガイドの例は次のとおりです。

default_permissions = ":workspace"
[allowed_permission_profiles]
":read-only" = true
":workspace" = true

ほかによく使う要件を、3つ挙げます。

  • ウェブ検索をキャッシュだけにする：allowed_web_search_modes = ["cached"] です。フルアクセスのセッションでも、その場の検索はできなくなります。
  • サインインを会社のワークスペースに限る：forced_login_method = "chatgpt" と forced_chatgpt_workspace_id の2つです。条件に合わない認証では、Codexはログアウトして終わります。
  • MCPサーバーを許可リストで絞る：名前と識別情報の両方が一致したサーバーだけが有効になります。

配り方は2つです。管理コンソールのエージェントセキュリティから配るか、端末やシステムにファイルを置きます。エージェントセキュリティではワークスペース全体の既定のほかに、ユーザー、グループ、ロールごとの上書きも作れます。

Codex Cloudのインターネット接続は、どう制御しますか？

環境ごとに、公開インターネットへ接続する範囲を選びます。すべての接続を許す設定をオフにして、パッケージマネージャーか、許可したドメインだけを通します。

Codex Cloudはクラウドの環境でタスクを実行する機能です。環境の設定画面には、次の3つの設定があります。

  • すべての公開インターネットへの接続を許可する設定
  • パッケージマネージャーのプリセット（npm、PyPI、crates.io、Mavenなどのレジストリ）
  • 追加で許可するドメイン

社内の非公開のサービスへはこれとは別のVPNの設定（Tailscale）でつなぎます。接続を許しても、そのサービスの認証情報や権限は付きません。

Codex Cloud（レガシー）の公式の解説は、エージェントに接続を許すと、次の危険が高まると書いています。接続を広げる前に、自社の対策を確かめます。

  • 信頼できないウェブの内容に紛れた指示（プロンプトインジェクション）
  • コードやシークレットの外部への流出
  • マルウェアや脆弱性のある依存関係の取り込み
  • ライセンス上の制約がある内容の取り込み

認証情報の渡し方

APIの鍵などはネットワークシークレットとして登録します。プログラムに渡るのは、置き換え用の文字列だけです。許可したドメインへのHTTPSの通信のときに、プロキシが本物の値に置き換えます。本物の値は環境の中のプロセスやファイルには渡りません。

クラウドの環境は社員の端末の設定やMDM（端末管理の仕組み）を引き継ぎません。端末に配った要件とは別に、クラウド側の要件を確かめます。

メールアドレスとパスワードでログインする社員は、Codex Cloudを使う前にMFA（多要素認証）の設定が必須です。SSOで入る会社には、SSOの管理者が全員にMFAを求めるよう、公式は案内しています。

データは学習に使われますか？保持と監査はどうなりますか？

Business、Enterprise、Edu、APIの業務データは、既定では学習に使われません。保持期間の設定、データレジデンシー、監査ログはEnterpriseとEduの機能です。

OpenAIの「Business data privacy, security, and compliance」によると、データは保存時にAES-256、通信時にTLS 1.2以上で暗号化されます。EKMを使うと、暗号鍵を自社で管理できます。

データレジデンシーは保存するデータの置き場所を地域で選ぶ仕組みです。対象のEnterprise、Edu、ChatGPT for Healthcare、APIの利用者は、日本を含む10の地域から選べます。

日本にデータを置くときの注意

GPT-6 Astraには、危険が疑われる動きを見つけるとタスクを止める、安全性の監視があります。米国外にデータを置く設定では、止まったタスクの検出結果を見られず、再開もできません。タスクはそのまま終わります。ゼロデータ保持の設定でも同じです。

日本にデータを置く会社は、試験導入の段階で、タスクが途中で終わったときの扱いを決めておきます。

監査ログと分析の使い分け

監査や調査には、Compliance APIを使います。記録をSIEMや電子証拠開示の仕組みへ書き出す用途です。公式は、このAPIをコードの品質や個人の業績の推定に使わないよう書いています。

利用の広がりを見る道具は、ワークスペース分析とAnalytics APIです。書き出した記録は自社の保存の決まりに従って守ります。OpenAI側の保存期間を、自社の保存の決まりの代わりにしないことも公式の注意点です。

CIなどの自動化には、アクセストークンとAPIキーのどちらを使いますか？

PlatformのAPIキーで済む自動化は、APIキーのままにします。ワークスペースの利用枠や管理の設定が要る、信頼できる自動化だけにCodexアクセストークンを使います。

項目Platform APIキーCodexアクセストークン
誰として動くかキーに紐づくAPIの組織とプロジェクトトークンを作った社員
使う枠と料金利用量に応じたAPI料金。ChatGPTの利用枠は使わないワークスペースで管理される利用資格を使う
使える所CLI、SDK、IDE拡張機能。GitHubのコードレビューなどのクラウドの機能は使えないCodex CLIとApp Serverによる、信頼できる環境での実行
使えるプランAPIの契約BusinessとEnterprise

アクセストークンは、作った社員として動きます。漏れると、手に入れた人が誰でもその社員として実行を始められます。公式が求める使い方は、次の4つです。

  • シークレットの管理の仕組みに保管し、ログに出さない
  • 公開のCI、フォークからのプルリクエスト、共有のマシンでは使わない
  • 関係のない複数のチームで、1人のトークンを使い回さない
  • 有効期限を付け、使わなくなったら取り消す

有効期限は7日、30日、60日、90日などから選び、最短は1日です。オーナーは新しいトークンに付けられる期限の上限を決められます。トークンを作れるのは、オーナーが権限を与えた社員だけです。

社員のローカル利用の権限を外しても、その社員のトークンは一時停止するだけで、取り消されません。退職や異動のときは、アクセストークンの画面でトークンを取り消します。オーナーと管理者は、ワークスペースのどのトークンでも取り消せます。

入れ替えの手順は4つです。新しいトークンを作り、実行環境のシークレットを更新します。新しいトークンで試しに動かし、最後に古いトークンを取り消します。

展開はどの順番で進め、稟議で何を聞かれますか？

公式の管理者向け導入ガイドは8つの段階を示しています。担当と範囲を決め、アクセスと要件を設定し、試験導入で確かめてから広げる流れです。

  1. 担当と範囲を決める：ワークスペース、ローカルの要件、Codex Cloud、接続先、記録の5つの領域ごとに担当を置きます。
  2. アクセスとIDを設定する：割り当てるのは、シート、グループ、ロールです。
  3. ローカルの実行の要件を配る：requirements.tomlで、承認とサンドボックスの範囲を固定します。
  4. リポジトリの設定をそろえる：設定、ルール、スキルの置き場所は、.codexか.agentsです。
  5. Codex Cloudを設定する：使う人、つなぐリポジトリ、接続先を決めます。
  6. プラグインと連携を確かめる：提供元、管理責任者、対象者、レビュー日を記録します。
  7. 監査と分析を設定する：連携に使う認証情報の置き場所は、自社のシークレットの管理の仕組みです。
  8. 試験導入で確かめる：許可した操作と止めた操作の両方を試します。

試す人数は、公式には決まりがありません。公式は、対象の利用者と管理者を代表するアカウントで、すべての管理範囲を確かめるよう求めています。実際に適用された設定と、各テストの結果を記録します。

TechWorkerも自社メディアの改修にCodexを使いました。2026年10月6日に記事55本を書き直し、公開前の点検で見つかった見出しの不具合12件を直しています。この点検はCodexが行ったもので、人が55本を1本ずつ確かめた記録とは扱いません。作業時間と費用も、公開用の記録からは分かりません。

稟議では次の項目を聞かれます。上から埋めると、決裁者が確かめたい点をひととおり押さえられます。

Codexの社内導入の稟議で聞かれること

□ 対象の部署・人数・期間と、ローカルとクラウドのどちらを使うか
□ プランの根拠（BusinessとEnterpriseの違いのうち、どれが要るか）
□ 6つの管理範囲ごとの担当者
□ requirements.tomlで禁じる設定（フルアクセス、承認なしの実行、その場のウェブ検索など）
□ データの扱い（学習、保持期間、置き場所）
□ 監査ログの取り方と、書き出した記録の保存の決まり
□ 自動化の認証の種類、トークンの期限と入れ替えの担当
□ 見直す条件（止めたはずの操作が止まらないとき、利用が広がらないとき）

社内の利用ルールの文面は、Claude Codeの社内展開のルールの雛形も参考になります。

よくある質問

Codexで入力したコードや業務データは、学習に使われますか？

BusinessとEnterpriseでは、既定で学習に使われません。OpenAIはChatGPT Business、Enterprise、Edu、APIのデータを、入力と出力を含めて既定で学習に使わないと書いています（2026年11月23日確認）。

Businessでも、グループごとに機能を分けるRBACを使えますか？

使えません。RBACとカスタムロールは、EnterpriseとEduの機能です。Businessの組み込みのロールはメンバー、管理者、オーナーの3つです。

社員がフルアクセス（--yolo）でCodexを動かすのを禁止できますか？

できます。requirements.tomlの allowed_sandbox_modes に read-only と workspace-write だけを書くと、フルアクセスを選べなくなります。allowed_approval_policies から never を外せば、承認なしの実行も選べません。

EnterpriseでCodex Cloudは、最初から使えますか？

既定ではオフです。管理者がクラウドでCodexを使う権限を対象の社員に付けます。以前のCodex Cloudで有効にしていたワークスペースは、その設定を引き継ぎます。

CodexアクセストークンはPlusやProでも使えますか？

使えません。Codexアクセストークンを使えるのは、ChatGPT BusinessとChatGPT Enterpriseのワークスペースです。CIなどの自動化にはPlatformのAPIキーも使えます。その場合はAPI料金で払います。

Codexのデータを日本に保存できますか？

対象のEnterprise、Edu、APIの利用者は、保存するデータの置き場所に日本を選べます。米国外に置く設定では、GPT-6 Astraの安全性の監視でタスクが止まると、そのタスクは再開できずに終わります。

自動レビューを使えば、人の承認は要らなくなりますか？

承認の依頼の多くを、レビュー担当のエージェントが代わりに審査します。ただし公式の説明では、安全を保証する仕組みではありません。判断を誤ることがあるため、サンドボックスの設計と監視は残すのが前提です。
