Claude Codeの活用

Claude Codeで既存コードを安全に直す実務研修｜調査・計画・テスト・レビューの進め方

Claude Codeで既存コードを直す研修は、90分の演習で、調べて・計画して・小さく直し・人が確認する型を身につけます。
Claude Codeの法人研修を設計する、担当者の方に向けた記事です。
再現、Plan Mode、小さな差分、テスト、人のレビューまでの演習設計と、成果の測り方が分かります。

Claude Codeで既存コードを直す研修では、何を教えるべきですか？

調べて、確認して、小さく直し、テストと人のレビューを通す一連の型を、持ち帰らせます。

Claude Codeの法人研修では、便利なコマンドやプロンプトを並べるだけでは足りません。既存コードを調べ、変更案を確認し、小さく直し、テストと人のレビューを通す型を教えます。

題材は、小さくて構いません。たとえば「入力が空のときだけエラーになる」という不具合です。意図しない変更を見つけて止める練習に、時間を使います。

Anthropicの公式資料も、日常の開発手順として案内しています。対象は、既存コードの探索、不具合修正、リファクタリング、テストです。Plan Modeでは、Claude Codeがファイルを読み、読み取り専用のコマンドで調査し、計画を示します。ソースファイルは編集しません[1]。研修ではこの性質を使い、編集前に人が変更範囲と検証方法を確認します。

型が必要な理由は、信頼が追いついていないことです。2025年のStack Overflow Developer Surveyの結果です。開発者が、49,000人を超えて回答しました[2]。

  • 84%が、AIツールを利用している、または利用予定です。
  • 出力精度を信頼しない人は46%、信頼する人は33%です。
  • 「ほぼ正しいが、完全には正しくない回答」に困るという回答は、66%に達しています。

研修の課題は、もっともらしい誤りを見抜く手順を、定着させることです。

DORAの2025年調査は、約5,000人への調査と、100時間を超える定性調査を行いました。結論は、AIは組織の強みと弱みを増幅する、というものです[3]。テストが遅い、完了条件が曖昧、レビューが属人的といった状態では、生成速度だけが上がり、手戻りが増えかねません。

TechWorkerは、Claude Codeを既存コードの改修にどう使っていますか？

代表の古野が毎日Claude Codeを使い、自社サービスの開発とメディアの改修にも使っています。

TechWorkerでは、代表の古野が毎日Claude Codeを使っています。用途は、自社サービスの開発、メディアの改修、営業資料の作成、毎朝の自動の集計です。

自社サービスの開発とメディアの改修は、どちらも既存のコードやファイルに手を入れる作業です。この記事の型は、その作業を安全に進める考え方に沿っています。

90分の演習は、どんな手順で進めますか？

準備のあと、調査15分、計画20分、修正とテスト40分、人のレビュー15分の順に進めます。

手順1　演習の前に、基準と権限を決める

研修の前に、再現コマンド、変更禁止範囲、受入条件を決めておきます。

実案件や機密コードは使いません。本番に似せた、小さな教材を用意します。

CLAUDE.mdには、テストコマンド、ディレクトリ構成、命名規則、毎回守る作業手順を書きます。禁止操作を確実に止めたい場合は、権限規則や事前フックを使います。教材環境、作業ディレクトリ、許可する操作を分けて確認します。

手順2　最初の15分：状況の確認と再現

受講者は、研修用リポジトリの状態、対象機能、テストコマンドを確認します。修正は、まだ頼みません。

「不具合を再現し、関係するファイル、原因の仮説、触らない範囲、検証方法を示す」と依頼します。ここで再現できなければ、編集へ進みません。

手順3　次の20分：Plan Modeで変更計画を作る

計画には、次を含めます。

  • 変えるファイル。
  • 変えないファイル。
  • 先に追加する再現テスト。
  • 想定する副作用。

受講者は、計画をそのまま承認しません。要求と違う箇所、広すぎる変更、根拠のない互換処理を指摘します。

手順4　続く40分：修正とテスト

1回の変更は、1原因に絞ります。複数の修正案をまとめて適用すると、どの変更が効いたのか追えなくなるためです。

修正前に、対象の不具合を再現するテストを1件追加します。まず失敗を確認します。修正後に、そのテストが通ることを確かめます。続けて、既存テスト、型検査、静的検査を実行します。

手順5　最後の15分：人がレビューして判断する

人が、要求との一致、副作用、読みやすさ、テストの妥当性を確認します。そのうえで、採用、差戻し、破棄のいずれかを選びます。

既存コードの修正研修は、どこでつまずきますか？

指示文書を安全装置とみなす、テストの通過で採用する、体感の時短で効果を測る、の3つが代表例です。

  • 指示文書に書いたから安全と考える。CLAUDE.mdは文脈を渡す仕組みで、強制設定ではありません。
  • 権限を省略するモードを、通常の研修で勧める。勧めるべきではありません。
  • 複数の修正案を、まとめて適用する。どの変更が効いたのか追えなくなります。
  • テストが通ったので、そのまま採用する。通過は採用を意味しません。期待値を書き換えて失敗を隠していないか、確認します。テストを無効化していないか、関係のないファイルまで直していないかも、差分で読みます。
  • 体感の時短だけで、効果を判断する。自己申告だけでは、研修効果を判断できません。

体感の時短を信用できない例があります。METRが2025年前半に実施した無作為化比較試験です。熟練したオープンソース開発者16人が、246件の実課題に取り組みました。AI利用時は、完了まで19%長くかかりました。参加者は、実際には遅くなった後も、20%速くなったと感じていました[7]。

範囲は、狭い研究です。大規模な既存プロジェクトに習熟した少人数の開発者と、2025年前半のツールが対象です。現在の全開発者へは、一般化できません。

METRの2026年更新では、高速化を示す生データも出ました。ただし、AIなしの作業を避ける参加者や、課題の選択偏りが大きくなりました。現在の生産性効果は、信頼できる形では推定できないと説明しています[8]。

Anthropic社内の利用例にも、疑似コード、テスト駆動、途中の介入を組み合わせる例があります。ただし、製品提供者の自社事例で、独立した効果測定ではありません[6]。

指示文書と権限設定は、どう使い分けますか？

指示文書は文脈を渡す仕組みで、禁止操作を確実に止めるのは権限規則や事前フックです。

手段役割強制力注意点
CLAUDE.md、AGENTS.mdテストコマンド、ディレクトリ構成、命名規則、毎回守る作業手順など、繰り返し説明する事実を渡す強制設定ではないAGENTS.mdの直接読込はClaude Code v2.1.277以降が対象。既定では、作業ディレクトリ以上にCLAUDE.mdやCLAUDE.local.mdがない場合に限られる。両方を使う場合は設定またはimportを確認し、/memoryで実際に読まれたファイルを確かめる
権限規則、事前フック禁止操作を確実に止める強制できる権限モードによって、ファイル編集やコマンド実行の扱いが変わる
Plan Modeファイルを読み、読み取り専用のコマンドで調査し、計画を示すソースファイルは編集しない調査用。通常の編集段階では、別の権限が働く

よくある質問

Claude Codeの研修では何を最初に教えるべきですか？

コマンドやプロンプトの小技より、1件の修正を完了する型です。不具合を再現し、変更計画を確認し、小さく直し、テストと人のレビューを通す流れを、小さな題材で繰り返し練習します。

CLAUDE.mdに禁止事項を書けば安全に使えますか？

書くだけでは足りません。CLAUDE.mdやAGENTS.mdは、繰り返し説明する事実を渡す仕組みで、強制設定ではありません。禁止操作を確実に止めるには、権限規則や事前フックを使う必要があります。

テストが通れば、AIの修正をそのまま採用してよいですか？

採用してはいけません。期待値の書き換えやテストの無効化、関係のないファイルの変更がないかを、差分で読みます。要求との一致と副作用を人が確認して、採用・差戻し・破棄を選びます。

次の一歩は、何から始めればよいですか？

小さな教材で90分の演習を1回行い、成果をAIなしの基準値と比べて測るところから始めます。

研修の効果は、完了時間に加えて、次の4つを、AIを使わない基準値と比べます。

  • 意図外変更。
  • レビューの差戻し。
  • 既存テストの失敗。
  • 同じ不具合の再発。

1件の修正を安全に終えられるかを観察し、失敗した工程を次の演習へ戻します。そこまで設計して初めて、現場で使える研修になります。
