Claude Codeの事例は、何を残せば別チームでも再現できますか？

入力、変更差分、実行コマンド、テスト結果、人の判断を一つの記録に残します。

社内紹介では、機密コードを掲載せず、許可判断とテストの型を共有します。これなら事例が広告文ではなく、次の担当者が使える作業手順になります。

公開事例では、各社はClaude Codeをどう導入していますか？

全社導入の公表、使い方の配布物化、結果の数字の公開に分かれます。8件とも原典を確認済みです。

出典URLは、記事末尾の出典リンク集にまとめました。

GMOデザインワン｜全エンジニア導入と、公表された目標値

GMOデザインワン株式会社は、2025年11月26日に全エンジニアへの『Claude Code』導入を発表しました（自社ニュースリリース）。作業時間を約50%短縮することを、目標に掲げています。

この「約50%」は目標値です。社内資料では、「同社が掲げた目標」として扱います。

ZOZO｜予算基準を先に決めて配り、その後で標準化した

株式会社ZOZOは、2025年7月29日に全エンジニアへの開発AIエージェント導入を発表しました（自社ニュースリリース）。基準は、1人あたり月額200米ドルです。導入前の調査・検証と、利用ガイドラインの作成も行っています。

約10ヶ月後の2026年6月8日、ZOZO TECH BLOGで記事が公開されました（田中秀明氏）。題は、「AI駆動開発を2コマンドで組織標準に」です。設計からテストまでを、/dev-initと/dev-resumeの2コマンドで標準にする取り組みです。配布から標準化までに、約10ヶ月かかっています。

メルカリ｜MDMでセキュリティ設定を組織配布する

株式会社メルカリのAI Security Teamは、2026年4月10日に公開された「Claude Code Meetup Japan #4」の登壇資料で、セキュリティ設定の組織配布戦略を発表しました（Hiroki Akamatsu氏）。題は、「メルカリのClaude Codeセキュリティ設定の組織配布戦略」です。Claude Codeにはファイル操作・Web検索・コマンド実行の機能があります。認証情報や重要ファイルへのアクセスを、リスクとして整理しています。配布する設定は、次のとおりです。

  • 人間による確認の義務化（パーミッションバイパスの禁止）
  • 危険なコマンド実行時の確認の必須化
  • 環境変数の読み込みとsudoの禁止
  • サンドボックスによるディレクトリ・ネットワークの制限
  • システムプロンプトへのセキュリティポリシーの追加

配布の手段は、MDM（端末管理）による一括展開です。エンジニアと非エンジニアの双方が、安全に使える環境を作る設計です。ルールを文書で周知せず、端末に配って既定値にします。設定項目の考え方は、Claude Codeの社内展開で解説しています。

サイボウズ｜個人の「秘伝のプロンプト」をPluginに変える

サイボウズ株式会社の技術ブログ「Cybozu Inside Out」では、2026年2月20日に事例が公開されています（齋藤氏）。手順や機能をまとめて配布する拡張機能（Plugin）を、チーム専用のマーケットプレイスで共有しました。各自の指示や手順を、再利用できる手順書（Skill）として集める取り組みです。プラグインは5カテゴリで、チーム規約強制系も含みます。規約を守らせる仕事を、目視のレビューから配布物に移しています。

構築直後は1個だったプラグインが、2ヶ月後には十数個に増えました。Issue作成数は、2025年の月平均約50件でした。2026年1月以降は、月換算で約80件ペースになったと報告されています。増加要因を単一の施策に帰属させる分析は、原典にありません。参考値として扱います。

LayerX｜イベント設計で属人化を崩す

LayerXのエンジニアブログでは、2025年9月22日にレポートが公開されています（さかい氏）。題は、「Claude Code Subagents祭」の開催レポートです。モバイルチームが、個人のサブエージェントをチームの共有知に変えた、短期集中イベントです。

進め方は5ステップです。各自のサブエージェントを共有し、適用先をブレストします。課題適性と頻度・影響をもとに、テーマを割り当てます。1週間の宿題形式で作り、デモ会で詰まりと次の一手を共有します。共通の詰まりどころに共通解ができたと書かれていますが、定量的な成果は原典にありません。

READYFOR｜効果と副作用を同じ調査で公開した

READYFOR株式会社は、2025年10月23日にZennの公式アカウントで社内アンケートの結果を公開しています（resqnet氏）。対象は社内開発チーム12名です。2025年7〜9月の3ヶ月間について、22項目で聞いています。

使用頻度は、毎日が67%、週数回が25%、時々が8%です。生産性向上の実感は83%、1日1〜2時間の時間短縮は66%、満足度は3.8／5点でした。一方で、疲労感の増加が42%、ストレスの増加が25%、生成コード品質のばらつきが66.7%でした。チーム共有の場を求める声は、67%です。12名の主観回答であり、ログ等による実測ではありません。効果と副作用を同じ調査で並べた点が、参考になります。

ナレッジワーク｜月448件のPR、ただし前提条件を必ず読む

株式会社ナレッジワークのZenn公式アカウントでは、2026年1月26日に活用事例が公開されています（sisisin氏）。データ基盤を担当する著者が、2025年12月に448件のコード変更提案（PR）をマージしたと報告しています。

同記事には「一人チーム・セルフマージOKの運用です」とあります。複数人のレビュー体制がある組織に、そのまま持ち込める数字ではありません。移植できるのは運用の工夫です。

  • 計画ファイル（plan.md）を先に出させ、計画段階で段取りをレビューします。
  • PreToolUse hookで、terraform・gcloud・dbtなどの危険なコマンドを制限します。
  • 人が担当する工程は、PRレビューだけに絞ります。
  • 記事執筆時点で、7並列のセッションを同時に張っています。

見出しの数字は移植の対象にせず、この順序と統制の置き方を借ります。

LG CNS｜20年ものの基幹システムを7ヶ月で移行した

Anthropic公式のカスタマーストーリーに、韓国のITサービス企業LG CNSの事例があります（2026年8月時点で公開）。20年稼働したシステムの刷新で、Claude Codeの複数の処理を管理し、順番に動かす仕組みを構築しました。

API移行は2,913件のうち2,888件（99.1%）、画面移行は1,340画面です。期間は7ヶ月（2025年11月〜2026年6月）で、コストは従来型のリビルドと比べて約50%削減されました。200名規模のBuild Centerで、標準の開発アプローチにしています。

Build Center責任者のHyosup Bae氏は、ROIについて次の趣旨を述べています。着手が難しかったプロジェクトを実行可能にしたことが、ROIだという内容です。

公開事例を踏まえて、自社ではどんな手順で始めますか？

対象業務とパイロット、予算、統制、標準化、職種の拡大の5つの順に、事例の工程設計を借ります。

事例を稟議へ引用する欄には、企業名、対象者、観測期間、目標か実績か、測定方法、自社と異なる条件を残します。READYFORの主観回答とナレッジワークの個人PR件数を、一つの効果率へまとめません。

  1. 対象業務を決め、パイロットを設計します。移行・変換・整備など、量が多く正解を定義できる作業から選びます。効果と副作用の両方を測る設問を、最初から入れます。
  2. 予算と契約を決めます。1人あたりの月額基準を、先に決めて配ります。詳しくはClaude Codeの導入コストをご覧ください。
  3. 統制を設計します。ルールの周知に頼らず、設定の配布と機械的な制約で効かせます。
  4. 使い方を標準にします。コツをそのまま共有せず、配布できる成果物に変換します。
  5. 職種を広げます。非エンジニアまで配る前提なら、統制を端末管理に載せます。詳しくは非エンジニアのClaude Code活用をご覧ください。

事例を参考にするとき、どんな失敗が起きやすいですか？

数字をそのまま期待値にする、最終形を真似る、配って終わりにする、の3つが目立ちます。

  • 数字をそのまま、自社の期待値にする。「50%効率化」という見出しを貼る前に、目標値か実績か、誰の数字かを確認します。組織規模の実測値として公開されている事例は、ごく限られています。
  • 先行企業の最終形を、そのまま真似る。サイボウズのPluginマーケットプレイスも、ZOZOの2コマンドも、使い込んだ結果として必要になったものです。小さく使って詰まりどころを見つけ、その詰まりを配布物に変えます。
  • ライセンスを配って終わりにする。ZOZOでは、配布から標準化まで約10ヶ月あります。READYFORでは、展開3ヶ月後に共有の場を求める声が67%出ています。

公開事例に共通するパターンは何ですか？

共通点は5つあります。配布と標準化の分離、統制の既定値化、共有の配布物化が中心です。

#共通パターン該当する公開事例
1「配る」と「使い方を標準にする」を別工程として進めているZOZO（配布2025年7月→標準化2026年6月）、READYFOR
2統制をルールの周知でなく、既定値・機械的な制約で効かせているメルカリ（MDMで設定配布）、ナレッジワーク（hook）
3共有の単位が「コツ」でなく、「インストールできる配布物」になっているサイボウズ（Plugin／Skill）、ZOZO、LayerX
4成果が出ている領域が、移行・変換・整備など反復量の多い作業に寄っているLG CNS、ナレッジワーク、ZOZO
5公開されている数字の性質がバラバラで、横並び比較できないGMOデザインワン（目標値）、ナレッジワーク（個人実績）、READYFOR（n=12の主観回答）

2025年前半のAI活用の共有は、「良いプロンプト集」でした。2026年の公開事例では、共有の単位が、Plugin・Skill・スラッシュコマンド・サブエージェントに変わっています。紹介した事例では、コツを配布物に変える取り組みが見られます。ただし、コマンド化すれば必ず使われるという比較検証ではありません。

次の一歩は何から始めればよいですか？

小規模なパイロットを、対象者・期間・評価指標を決めてから始めます。配布後の標準化も計画に入れます。

TechWorkerは、上場企業を含む37社・2,500名の生成AI導入・活用を支援し、この工程設計を伴走してきました。他社事例のどこが自社に移植でき、どこが前提条件ごと違うのかの見極めから、ご相談いただけます。
